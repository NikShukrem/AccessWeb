# AccessWeb v3

Веб-система управления логистикой — замена MS Access. Ноутбук выступает сервером, фронтенд отдаётся тем же сервером (и дублируется на GitHub Pages).

## Быстрый старт

### Запуск (один способ, без путаницы)

Двойной клик по ярлыку **AccessWeb** на рабочем столе (или `run.bat` в корне репозитория).

Скрипт сам:
1. подтягивает последнюю версию из GitHub (`git pull`), если нет несохранённых локальных правок;
2. ставит зависимости при первом запуске;
3. запускает сервер на `http://localhost:8080`.

**Важно:** запускайте только из этой папки. Если где-то есть вторая копия репозитория — она рано или поздно разъедется по версии кода с этой. Один репозиторий — один способ запуска.

Если нужно запустить без проверки обновлений (например, офлайн) — используйте `start.bat` напрямую.

### Доступ из интернета (туннель)

Для доступа не из офисной сети (удалённо, из другой страны и т.д.) нужен туннель:

```
tunnel.bat
```

Требует `cloudflared.exe` рядом со скриптом, на рабочем столе или в Загрузках ([скачать](https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-windows-amd64.exe)). Туннель выдаст URL вида `https://xxxx-xxxx.trycloudflare.com` — это адрес для всех внешних пользователей.

## Возможности

- **Грузы (ACID), договоры, контрагенты, транзакции (АИС)** — полный учёт логистики с формами, поиском и фильтрами, как в исходном Access. Форма добавления договора сворачивается до основных полей одной кнопкой.
- **Стадии договоров** — отдельная вкладка ведения этапов/подэтапов договора (номер, ответственный, план/факт даты, статус) с добавлением, редактированием, быстрым завершением и удалением; кнопка загрузки типового процесса согласования (Подготовка → НМЦ → Закупка → Заключение договора) с автоматическим расчётом плановых дат по рабочим дням от даты старта.
- **Диаграмма Ганта по этапам** — визуализация стадий договоров (Chart.js), фильтр по договорам чипами, разбивка по статусам (ожидает/в работе/завершён/просрочен).
- **Импорт из Excel/CSV** — перенос данных без ручного перевода.
- **Дашборд** — сводные цифры по договорам/грузам/платежам плюс круговые и столбчатые графики.
- **Глобальный поиск** (только `admin`/`director`) — сквозной поиск по грузам, договорам, счетам, контрагентам и номенклатуре счетов; переключатель «везде» / «по выбранным категориям».
- **Конструктор отчётов** (только `admin`/`director`) — блочный конструктор (таблица → поля → условия → сортировка) генерирует SQL, который можно доработать вручную; результат — таблица, запросы можно сохранять и запускать повторно. Только `SELECT`-запросы, доступ к таблицам приложения.
- **CRM задач для руководителя** — назначение задач сотрудникам, канбан-доска (5 статусов), приоритеты и просрочки, чек-листы и комментарии внутри задачи, перетаскивание карточек между статусами, привязка задачи к конкретному грузу, договору или счёту, фильтры и поиск; вкладка «Сотрудники» — загрузка по всем сотрудникам (включая тех, у кого пока 0 задач), список сотрудников для назначения обновляется сразу при добавлении/удалении пользователя.
- **Уведомления** — колокольчик со счётчиком непрочитанных, клик по уведомлению открывает нужную задачу.
- **Профиль «Египет»** — отдельная облегчённая страница (`egypt.html`) без тяжёлых библиотек (Chart.js/PapaParse/XLSX), для работы на медленном интернете.
- **Роли и доступ** — у каждой роли свой набор разделов и прав на импорт/удаление.
- **Журнал аудита** — для ролей «Директор» и «Администратор»: кто, когда и что создал, изменил, удалил или прикрепил, с фильтрами по таблице и типу действия.
- **Пользователи** (только `admin`) — список сотрудников с ролью и отделом, добавление нового пользователя, смена пароля любому существующему.

## Аудит кода

Дата: 2026-08-25 (обновлено; исходный аудит — 2026-07-10). Текущий объём: `index.html` — ~5030 строк, `backend/src/server.js` — ~1760 строк, 31 маршрут (42 обработчика с учётом всех HTTP-методов), 8 основных таблиц данных плюс `saved_reports`, `tasks`/`attachments`/`audit_log`/`notifications`.

Сильные стороны:

- Единая точка входа для CRUD (`/:table`) с явным белым списком таблиц (`VALID_TABLES`) и колонок (`ALLOWED_COLUMNS`) — новый функционал не открывает случайных полей на запись.
- Ролевая модель (`ROLE_PERMISSIONS`) отделена от бизнес-логики маршрутов — права проверяются одним общим механизмом (`checkAccess`, `canReadTable`, `canWriteTable`, `canDeleteTable`), а не разбросаны по каждому обработчику.
- Идемпотентные миграции (`runMigrations`) — схема обновляется автоматически при старте сервера без ручных SQL-скриптов.
- Ошибки со стороны сервера всегда возвращают общий текст клиенту и пишут детали только в серверный лог — стек вызовов наружу не уходит.
- Разовые скрипты обслуживания данных вынесены в `backend/seed/` — большинство (`backfill_demo_data.js`, `fix_transaction_contract_links.js`) не подключаются к серверу, можно удалять/прогонять повторно без риска. Исключение — `demoEmployees.js`: его при каждом старте динамически подключает `seedUsers()` в `server.js` (в `try/catch`, необязательно) для автосоздания демо-аккаунтов, если их ещё нет; удаление файла просто отключает этот шаг, без ошибки.
- Конструктор отчётов (`/reports/run`) ограничен только `SELECT`/`WITH`, блокирует опасные ключевые слова и составные запросы, результат оборачивается в `LIMIT 500` — доступен только `admin`/`director`.
- **2026-08-25**: прошёлся по всему коду и убрал мёртвый код — две неиспользуемые функции экспорта/шаблонов CSV в `index.html` (кнопки на них были удалены ещё в июне, функции остались сиротами), 4 CSS-правила без единого применения (`.btn-action`, `.metric-big`, `.text-danger`, `.section-card`), две устаревшие ручные резервные копии базы (`backend/data/*.bak-*`, не в git). Backend-хелперы и маршруты — все использующиеся, мёртвого кода не найдено.
- **2026-08-25, второй проход** (после добавления «Стадии договоров», Ганта, конструктора отчётов, поиска, «Пользователи»): агентом перепроверены все JS-функции, CSS-классы и backend-маршруты. Найдены и убраны ещё 3 неиспользуемых маршрута — `GET /tasks/:id/comments` (комментарии уже приходят внутри `GET /tasks/:id`, отдельный список фронтенд не запрашивал), `DELETE /tasks/:id/checklist/:itemId` и `PUT /ais_transactions/:id/items/:itemId` (фронтенд их не вызывал — только добавление/переключение/удаление позиций и чек-листа) — и один неиспользуемый CSS-класс `.metric-card`. Ещё две накопившиеся вручную резервные копии базы удалены с диска. `demoEmployees.js` — не мёртвый код, подключается динамически из `seedUsers()`.

Найденные проблемы (не связанные с безопасностью, см. раздел ниже):

- `express-validator` в зависимостях (`backend/package.json`) по-прежнему нигде не используется — валидация тела запроса сделана вручную в каждом обработчике. Зависимость стоит либо удалить, либо начать использовать по назначению.
- Некоторые проверки согласованности данных (например, договор счёта должен совпадать с договором его ACID) реализованы как разовые скрипты-фиксы поверх уже испорченных данных, а не как ограничение на уровне схемы (constraint/trigger). Работает, но при появлении нового похожего сценария рассинхронизации потребуется новый скрипт.
- Фронтенд — один файл на 5000+ строк без сборки и модулей. Для текущего размера команды это осознанный компромисс (проще разворачивать), но дальнейший рост функциональности стоит сопровождать разделением на модули.
- **Поиск и «содержит» в конструкторе отчётов регистрозависимы для кириллицы.** Установленная сборка `sqlite3` не поддерживает регистрацию кастомных SQL-функций (`db.function()` отсутствует в нативном модуле) — обойти штатный `LIKE`/`LOWER()`, которые понимают регистр только для ASCII, нельзя чисто через SQL. Глобальный поиск (`/search`) починен: сравнение вынесено в JS (`toLowerCase()`, корректно для кириллицы) поверх выборки всех строк — таблицы небольшие (до ~8000 строк), это дёшево. В конструкторе отчётов это невозможно (там произвольный SQL пользователя, а не фиксированный набор колонок) — оператор «содержит» там всё ещё регистрозависим для кириллицы.
- `GET /auth/me` реализован (возвращает свежие данные пользователя из БД), но фронтенд его не вызывает — сейчас профиль берётся из `localStorage`, установленного при логине. Не мёртвый код в строгом смысле (маленький, корректный, стандартный для JWT-auth эндпоинт), но использования пока нет.

## Аудит безопасности

Дата: 2026-07-10, дополнено 2026-08-25.

### Устранено в ходе аудита

- **Критично.** `express.static(join(__dirname, '../../'))` отдавал как статику весь корень репозитория, включая `backend/data/accessweb.db` (полная база данных, включая хэши паролей всех пользователей) и файлы из `backend/seed/`. Любой, кто знал адрес сервера, мог скачать `GET /backend/data/accessweb.db` без авторизации. Подтверждено на живом продакшн-сервере до исправления. Строка полностью удалена — `index.html`, `egypt.html` и `sw.js` уже обслуживаются отдельными маршрутами, других локальных статических ресурсов приложению не требуется.
- **Нет аудит-лога действий пользователей** (был в списке открытых рисков ниже) — устранено. Добавлена таблица `audit_log` и логирование создания/изменения/удаления записей и загрузки/удаления вложений: кто, когда, в какой таблице, какая запись, какие поля изменились (для удаления — снимок всей строки, раз восстановить её после удаления уже нельзя). Просмотр — вкладка «Журнал аудита» и эндпоинт `GET /audit-log`, доступны только ролям `admin` и `director`.

### Что уже реализовано правильно

- Пароли хранятся только в виде bcrypt-хэшей, в открытом виде нигде не логируются и не возвращаются клиенту.
- Авторизация через JWT с ограниченным сроком действия (12 часов); все защищённые маршруты проверяют токен через единый middleware `auth`.
- Rate-limiting отдельно для входа (`authLimiter` — 20 попыток за 15 минут) и для остального API (`apiLimiter` — 300 запросов в минуту), защита от перебора паролей и грубого DoS через API.
- CORS ограничен явным списком разрешённых источников (`ALLOWED_ORIGINS`), а не открыт на все домены.
- Заголовки безопасности выставлены через `helmet`, включая Content-Security-Policy.
- Загрузка вложений (`/attachments`) проверяет расширение файла по белому списку, ограничивает размер (15 МБ), сохраняет файлы под сгенерированным UUID-именем (оригинальное имя пользователя нигде не используется как путь на диске — исключает path traversal), и проверяет права на чтение/запись/удаление по роли и по владельцу файла.
- Генерическая таблица CRUD не даёт передавать произвольное имя таблицы или колонки в SQL — оба варианта сверяются с белым списком до формирования запроса.
- Данные о пользователе в каждом запросе берутся из проверенного JWT (`req.user`), а не из тела запроса — нет способа выдать себя за другого пользователя, подделав поле `user_id`.
- **Конструктор отчётов (`/reports/run`, добавлен 2026-08-25)** — новая поверхность атаки: пользователь пишет произвольный SQL. Ограничен ролями `admin`/`director`, только `SELECT`/`WITH`, блок-лист DDL/DML-ключевых слов, запрет составных запросов (`;`), результат оборачивается в `SELECT * FROM (...) LIMIT 500`. Сохранённые отчёты (`saved_reports`) удаляют только автор или `admin`.

### Открытые риски (не устранялись в рамках этой сессии, требуют решения перед выходом на прод у внешнего заказчика)

1. **JWT_SECRET по умолчанию.** Если переменная окружения `JWT_SECRET` не задана, сервер стартует с захардкоженным dev-значением (с предупреждением в лог, но без остановки). На проде обязательно должен быть установлен свой секрет — шаблон `backend/.env.production` уже содержит инструкцию и заглушку, которую нужно заменить перед запуском.
2. **Демонстрационные учётные записи с публично известными паролями.** Логины/пароли по умолчанию (`admin/admin123`, `director/director123` и т.д.) заведены автоматически при первом запуске и перечислены в этом README. Перед реальным внедрением у заказчика — обязательно сменить все пароли или отключить дефолтных пользователей.
3. **Нет самостоятельной смены пароля.** Администратор теперь может сменить пароль любому сотруднику через интерфейс (`PUT /users/:id/password`, только `admin`, действие пишется в журнал аудита без самого пароля) — это закрывает часть риска (не нужна правка базы руками), но сотрудник по-прежнему не может сам оперативно сменить свой пароль при компрометации учётной записи — для этого нужен отдельный эндпоинт `/auth/change-password` с проверкой текущего пароля.
4. **JWT хранится в `localStorage`.** Это стандартный подход для SPA, но означает, что успешная XSS-атака на фронтенд даёт доступ к токену. Учитывая, что CSP уже разрешает `'unsafe-inline'` для скриптов (из-за встроенных `onclick=`), риск XSS выше, чем при строгом CSP без inline-обработчиков. Снижение риска — либо переход на httpOnly-cookie для токена, либо постепенный отказ от инлайновых обработчиков в пользу `addEventListener`.
5. **HTTPS не встроен в сам сервер.** Express слушает обычный HTTP; шифрование трафика предполагается через внешний reverse proxy (nginx) или туннель (Cloudflare, уже используется для удалённого доступа). При прямом доступе по локальной сети без прокси трафик, включая пароли при логине, не шифруется.
6. **SQLite как единственное хранилище.** Подходит для текущей нагрузки (до ~50-100 одновременных пользователей), но не имеет встроенного шифрования на уровне файла — при физическом доступе к серверу (или, до сегодняшнего исправления, при сетевом доступе) файл базы читается без дополнительной защиты. При повышенных требованиях к конфиденциальности — рассмотреть шифрование диска на уровне ОС или переход на PostgreSQL с TLS.
