# AccessWeb v3

Веб-система управления логистикой — замена MS Access. Ноутбук выступает сервером, фронтенд отдаётся тем же сервером (и дублируется на GitHub Pages).

## Быстрый старт

### Запуск (один способ, без путаницы)

Двойной клик по ярлыку **AccessWeb** на рабочем столе (или `run.bat` в корне репозитория).

Скрипт сам:
1. подтягивает последнюю версию из GitHub (`git pull`), если нет несохранённых локальных правок;
2. ставит зависимости при первом запуске;
3. запускает сервер на `http://localhost:8080`.

**Важно:** запускайте только из этой папки. Если где-то есть вторая копия репозитория — она рано или поздно разъедется по версии кода с этой. Один репозиторий — один способ запуска.

Если нужно запустить без проверки обновлений (например, офлайн) — используйте `start.bat` напрямую.

### Доступ из интернета (туннель)

Для доступа не из офисной сети (удалённо, из другой страны и т.д.) нужен туннель:

```
tunnel.bat
```

Требует `cloudflared.exe` рядом со скриптом, на рабочем столе или в Загрузках ([скачать](https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-windows-amd64.exe)). Туннель выдаст URL вида `https://xxxx-xxxx.trycloudflare.com` — это адрес для всех внешних пользователей.

## Возможности

- **Грузы (ACID), договоры, контрагенты, транзакции (АИС)** — полный учёт логистики с формами, поиском и фильтрами, как в исходном Access.
- **Импорт из Excel/CSV** — перенос данных без ручного перевода.
- **Дашборд** — сводные цифры по договорам/грузам/платежам плюс круговые и столбчатые графики.
- **CRM задач для руководителя** — назначение задач сотрудникам, канбан-доска (5 статусов), приоритеты и просрочки, чек-листы и комментарии внутри задачи, перетаскивание карточек между статусами, привязка задачи к конкретному грузу или договору, фильтры и поиск.
- **Уведомления** — колокольчик со счётчиком непрочитанных, клик по уведомлению открывает нужную задачу.
- **Профиль «Египет»** — отдельная облегчённая страница (`egypt.html`) без тяжёлых библиотек (Chart.js/PapaParse/XLSX), для работы на медленном интернете.
- **Роли и доступ** — у каждой роли свой набор разделов и прав на импорт/удаление.

## Доступ

- **Офис**: `http://localhost:8080` или `http://[IP-ноута]:8080`
- **Удалённо** (Египет и другие): URL, который выдаёт `tunnel.bat`
- **GitHub Pages**: `https://nikshukrem.github.io/AccessWeb/` (статичный фронтенд, работает вместе с туннелем — см. поле «Адрес сервера» на странице входа)

## Аудит кода

Дата: 2026-07-10. Объём на момент аудита: `index.html` — 3823 строки, `backend/src/server.js` — около 1550 строк, 36 REST-маршрутов, 7 основных таблиц данных.

Сильные стороны:

- Единая точка входа для CRUD (`/:table`) с явным белым списком таблиц (`VALID_TABLES`) и колонок (`ALLOWED_COLUMNS`) — новый функционал не открывает случайных полей на запись.
- Ролевая модель (`ROLE_PERMISSIONS`) отделена от бизнес-логики маршрутов — права проверяются одним общим механизмом (`checkAccess`, `canReadTable`, `canWriteTable`, `canDeleteTable`), а не разбросаны по каждому обработчику.
- Идемпотентные миграции (`runMigrations`) — схема обновляется автоматически при старте сервера без ручных SQL-скриптов.
- Ошибки со стороны сервера всегда возвращают общий текст клиенту и пишут детали только в серверный лог — стек вызовов наружу не уходит.
- Разовые скрипты обслуживания данных вынесены в `backend/seed/` и не подключаются к серверу — их можно удалить или прогнать повторно без риска для приложения.

Найденные проблемы (не связанные с безопасностью, см. раздел ниже):

- `express-validator` в зависимостях (`backend/package.json`) нигде не используется — валидация тела запроса сделана вручную в каждом обработчике. Зависимость стоит либо удалить, либо начать использовать по назначению.
- Резервные копии базы (`backend/data/*.bak-*`) создавались вручную и накапливались в рабочей папке без ротации — добавлены в `.gitignore`, но нужен процесс автоматической очистки старых копий.
- Некоторые проверки согласованности данных (например, договор счёта должен совпадать с договором его ACID) реализованы как разовые скрипты-фиксы поверх уже испорченных данных, а не как ограничение на уровне схемы (constraint/trigger). Работает, но при появлении нового похожего сценария рассинхронизации потребуется новый скрипт.
- Фронтенд — один файл на 3800+ строк без сборки и модулей. Для текущего размера команды это осознанный компромисс (проще разворачивать), но дальнейший рост функциональности стоит сопровождать разделением на модули.

## Аудит безопасности

Дата: 2026-07-10.

### Устранено в ходе аудита

- **Критично.** `express.static(join(__dirname, '../../'))` отдавал как статику весь корень репозитория, включая `backend/data/accessweb.db` (полная база данных, включая хэши паролей всех пользователей) и файлы из `backend/seed/`. Любой, кто знал адрес сервера, мог скачать `GET /backend/data/accessweb.db` без авторизации. Подтверждено на живом продакшн-сервере до исправления. Строка полностью удалена — `index.html`, `egypt.html` и `sw.js` уже обслуживаются отдельными маршрутами, других локальных статических ресурсов приложению не требуется.
- Эмодзи-маркеры убраны из `backend/.env.example` и `backend/.env.production` (не проблема безопасности сама по себе, но приведено в соответствие с общим стилем документации).

### Что уже реализовано правильно

- Пароли хранятся только в виде bcrypt-хэшей, в открытом виде нигде не логируются и не возвращаются клиенту.
- Авторизация через JWT с ограниченным сроком действия (12 часов); все защищённые маршруты проверяют токен через единый middleware `auth`.
- Rate-limiting отдельно для входа (`authLimiter` — 20 попыток за 15 минут) и для остального API (`apiLimiter` — 300 запросов в минуту), защита от перебора паролей и грубого DoS через API.
- CORS ограничен явным списком разрешённых источников (`ALLOWED_ORIGINS`), а не открыт на все домены.
- Заголовки безопасности выставлены через `helmet`, включая Content-Security-Policy.
- Загрузка вложений (`/attachments`) проверяет расширение файла по белому списку, ограничивает размер (15 МБ), сохраняет файлы под сгенерированным UUID-именем (оригинальное имя пользователя нигде не используется как путь на диске — исключает path traversal), и проверяет права на чтение/запись/удаление по роли и по владельцу файла.
- Генерическая таблица CRUD не даёт передавать произвольное имя таблицы или колонки в SQL — оба варианта сверяются с белым списком до формирования запроса.
- Данные о пользователе в каждом запросе берутся из проверенного JWT (`req.user`), а не из тела запроса — нет способа выдать себя за другого пользователя, подделав поле `user_id`.

### Открытые риски (не устранялись в рамках этой сессии, требуют решения перед выходом на прод у внешнего заказчика)

1. **JWT_SECRET по умолчанию.** Если переменная окружения `JWT_SECRET` не задана, сервер стартует с захардкоженным dev-значением (с предупреждением в лог, но без остановки). На проде обязательно должен быть установлен свой секрет — шаблон `backend/.env.production` уже содержит инструкцию и заглушку, которую нужно заменить перед запуском.
2. **Демонстрационные учётные записи с публично известными паролями.** Логины/пароли по умолчанию (`admin/admin123`, `director/director123` и т.д.) заведены автоматически при первом запуске и перечислены в этом README. Перед реальным внедрением у заказчика — обязательно сменить все пароли или отключить дефолтных пользователей.
3. **Нет самостоятельной смены пароля.** Сейчас пароль меняется только прямой правкой базы администратором. При компрометации учётной записи сотрудник не может сам оперативно сменить пароль — нужен отдельный эндпоинт `/auth/change-password` с проверкой текущего пароля.
4. **JWT хранится в `localStorage`.** Это стандартный подход для SPA, но означает, что успешная XSS-атака на фронтенд даёт доступ к токену. Учитывая, что CSP уже разрешает `'unsafe-inline'` для скриптов (из-за встроенных `onclick=`), риск XSS выше, чем при строгом CSP без inline-обработчиков. Снижение риска — либо переход на httpOnly-cookie для токена, либо постепенный отказ от инлайновых обработчиков в пользу `addEventListener`.
5. **Нет аудит-лога действий пользователей.** Кто именно изменил или удалил запись — фиксируется только полями `responsible`/`uploaded_by` на отдельных сущностях, отдельного журнала действий (кто/когда/что) нет. Требуется, если заказчику важна прослеживаемость изменений.
6. **HTTPS не встроен в сам сервер.** Express слушает обычный HTTP; шифрование трафика предполагается через внешний reverse proxy (nginx) или туннель (Cloudflare, уже используется для удалённого доступа). При прямом доступе по локальной сети без прокси трафик, включая пароли при логине, не шифруется.
7. **SQLite как единственное хранилище.** Подходит для текущей нагрузки (до ~50-100 одновременных пользователей), но не имеет встроенного шифрования на уровне файла — при физическом доступе к серверу (или, до сегодняшнего исправления, при сетевом доступе) файл базы читается без дополнительной защиты. При повышенных требованиях к конфиденциальности — рассмотреть шифрование диска на уровне ОС или переход на PostgreSQL с TLS.
